# План: универсальный сервис для проведения конференций (на базе jury-score)

## Контекст

Сейчас `jury-score` — одноразовый инструмент для одной конференции (RWP-2026): 23 доклада зашиты в `TALKS` в `index.html`, критерии — в `CONFIG`, бэкенд — Apps Script с Google-таблицей. Программу организаторы собирают вручную в Word/PDF. Отсюда ошибки: в программе RWP-2026 сбито время секции 4 («14:45 – 14:00»). Протоколы, таблички «на дверь» и дипломы тоже делаются вручную.

**Цель** — универсальный сервис для конференций и мероприятий. Главный сценарий будущего:

> Пользователь даёт чат-боту материалы (информационное письмо, список заявок, регламент). Бот через API сервиса **сам создаёт программу целиком** и отдаёт человеку **ссылку-приглашение**. По ссылке человек получает аккаунт с уже собранной программой и правит её в конструкторе.

Дальше в сервисе: публичная программа для участников, печать документов, конкурс докладов с оценкой жюри, приём заявок. Ни строчки кода не должно зависеть от конкретной конференции.

**Решения пользователя:**
- **Хранение:** свой сервер, PocketBase + SQLite на VPS под `konkin-nikita.ru`.
- **Модули:** конструктор, публичная программа, документы, жюри; ввод вручную, из Excel/CSV и через заявки.
- **Чат-боты:** Claude (Desktop/Code), ChatGPT, GigaChat/YandexGPT, локальная модель в LM Studio.
- **Создание через бота — только по API-ключу**, который выдаёте вы.
- **Бот возвращает ссылку-приглашение**, а не пароль.
- **У ботов есть канал обратной связи:** если функции не хватает, бот сообщает об этом, а вы видите сгруппированный список того, чего не хватает на практике.
- **Сначала мобильная версия, потом десктопная.** Это касается всех модулей, включая конструктор.
- **Поддержка устройств и браузеров с 2018 года:** iOS 12+ (iPhone 5s/6, iPad Air 1, iPad mini 2), Android 5+ с Chrome 61+, Яндекс.Браузер, Samsung Internet 8+, Firefox 60+, Edge 79+. Минимальная ширина экрана 320 px (iPhone 5s).

**Ограничение на сегодня:** сайт `jury-score` работает в день конференции, его не трогаем. Новый сервис делается в **новом репозитории**.

## Архитектура

```
Чат-боты                                     Браузер (владелец / участник / жюри)
  Claude Desktop/Code, LM Studio ─ MCP stdio      │
  Claude Code, LM Studio ───────── MCP HTTP       │
  ChatGPT ──────────────────────── GPT Actions (OpenAPI + ключ)
  GigaChat, YandexGPT ──────────── JSON → страница «Создать из JSON»
        │  API-ключ                                │ HTTPS, REST + realtime
        ▼                                          ▼
conf.konkin-nikita.ru (VPS в РФ)
  ├─ PocketBase: pb_public/ (фронтенд), pb_hooks/ (/api/v1/*, жюри, cron), pb_migrations/, pb_data/
  ├─ mcp/ (Node, @modelcontextprotocol/sdk) — обёртка над /api/v1
  └─ /llms.txt, /schema/program.v1.json, /openapi.json — «инструкция» для ботов
```

- **Сервер в РФ:** быстрые ответы, а ПДн участников хранятся в РФ, как требует 152-ФЗ.
- **Фронтенд: Preact + лёгкая сборка esbuild** (одна команда `npm run build` → `dist/` → `pb_public`). Без сборки старые браузеры не справятся: синтаксис `?.`, `??` и object spread валит скрипт целиком на Safari 12 и Chrome 61–79.
  - esbuild переводит JS и CSS под цели `safari12, ios12, chrome61, firefox60, edge79` и делит код по маршрутам. Тяжёлые SheetJS и docx загружаются только на своих экранах.
  - Полифилы подключаются по проверке возможностей, только там, где их нет: `AbortController` (его нет в iOS 12.0), `Array.prototype.flat/flatMap`, `Object.fromEntries`, `Promise.prototype.finally`, `IntersectionObserver`, `ResizeObserver`.
  - Для старых браузеров: если нет поддержки модулей, `fetch` или `Promise`, вместо пустой страницы показывается «Браузер устарел» с советом установить Яндекс.Браузер или Chrome. Это делает `nomodule`-скрипт и встроенная ES5-проверка.
  - Внешних CDN нет, всё собирается в свой бандл.
- **`shared/model.js`** — одна реализация, которая работает в браузере, в Node (MCP) и в goja (pb_hooks). Это classic-скрипт с `module.exports`-фолбэком. Внутри:
  - нормализация («И. О. Фамилия», организации);
  - авто-время;
  - проверки;
  - сравнение версий.

## Сначала мобильная версия, поддержка старых устройств

**Мобильная версия (этапы 3–7):** каждый экран сначала делается для ширины 320–390 px, проверяется на 320 px и только потом расширяется.
- **Управление пальцем:**
  - элементы не меньше 44 px;
  - ничего не прячется за hover;
  - редактирование — в нижних листах (bottom sheet);
  - основные действия — на закреплённой панели снизу с учётом `safe-area`.
- **Конструктор на телефоне** устроен как навигация вглубь: мероприятие → день → заседание → элементы.
  - Порядок меняется долгим нажатием с перетаскиванием (SortableJS работает с касаниями и на старых браузерах) или кнопками «↑ / ↓ / Переместить в…». Кнопки работают везде и не требуют точных жестов.
  - Ошибки проверки показываются значками на элементах и списком в отдельном листе.
- **Документы на телефоне:** предпросмотр A4 в масштабе и кнопка «Скачать PDF». На старых iOS и Android печать из браузера ненадёжна, поэтому PDF собирается на сервере: Gotenberg в Docker рядом с PocketBase, нужен VPS с 2 ГБ памяти.
- **Медленная сеть и слабые устройства:**
  - публичная программа и жюри — не больше 80 КБ JS в gzip;
  - кэш данных в localStorage;
  - офлайн-очередь жюри (уже есть в jury-score).

**Десктопная версия (этап 8)** — поверх готовой мобильной, от 900 px:
- конструктор в несколько колонок (дерево дней и заседаний | список элементов | редактор);
- перетаскивание между заседаниями, горячие клавиши;
- широкие таблицы людей, заявок и результатов жюри;
- предпросмотр печатной программы рядом с редактором.

**Liquid glass на старых и слабых устройствах:**
- без `backdrop-filter` (проверка через `@supports`), при `prefers-reduced-transparency`, а также на слабом железе (`deviceMemory ≤ 2`, `hardwareConcurrency ≤ 4`) у `<html>` ставится класс `lite`: непрозрачные панели, без размытия и тяжёлых теней;
- запрещены свойства, которых нет в Safari 12 и Chrome 61: `inset`, `gap` у flex-контейнеров (только у grid), `color-mix()`, `:is()`, `:has()`, `aspect-ratio`. В jury-score `inset` и flex-`gap` использовались — при переносе стилей их надо заменить на `top/right/bottom/left`, отступы и grid. Это ловит линтер (stylelint-no-unsupported-browser-features).

## Центральный артефакт: документ программы `conf.program/v1`

Одна JSON-схема, понятная и человеку, и LLM. Это формат API для ботов, импорта и экспорта, резервной копии и шаблона «скопировать прошлое мероприятие». Программа RWP-2026 переносится в него как фикстура и образец для ботов.

```json
{
  "schema": "conf.program/v1",
  "event": { "title": "...", "date_from": "2026-10-07", "date_to": "2026-10-09", "city": "Йошкар-Ола",
             "venue": "ПГТУ", "regulations": { "talk_min": 15, "plenary_min": 30 },
             "jury": { "criteria": ["Актуальность темы", "..."], "scale_max": 5 } },
  "sections": [{ "no": 1, "title": "Дистанционное зондирование ..." }],
  "days": [{ "date": "2026-10-07", "sessions": [{
      "title": "Заседание №1", "room": "ауд. 431", "start": "09:00",
      "chair": "Н. В. Рябова, д.ф.-м.н., профессор", "cochair": "...", "secretary": "...",
      "items": [
        { "type": "talk", "section": 1, "title": "...", "authors": ["Д. М. Караваев", "Е. С. Беленя"],
          "speaker": "Е. С. Беленя", "format": "online", "org": "ВКА им. А. Ф. Можайского", "city": "Санкт-Петербург" },
        { "type": "break", "title": "Кофе-брейк", "duration": 30, "room": "ауд. 436" },
        { "type": "plenary", "start": "11:00", "title": "...", "speaker": "Н. Л. Истомина" } ] }] }]
}
```

- `start` и `duration` можно не указывать. Время рассчитывается по регламенту, а явный `start` служит якорем.
- Люди и организации задаются строками. Сервер сам нормализует их и связывает со справочниками.
- В отчёте проверки ошибки и предупреждения — с путём (`days[0].sessions[1].items[3]`) и текстом на русском. Бот исправляет их и отправляет программу снова.
- **Поле `extra`** есть у мероприятия, заседания и элемента. Туда бот кладёт данные, которым нет места в схеме: например, ссылку на онлайн-трансляцию или стендовую сессию с номерами стендов. Сервер хранит их как есть и показывает в конструкторе, так что ничего не теряется. В отчёте проверки появляется предупреждение «данные вне схемы». Каждый такой случай автоматически попадает в обратную связь, и видно, каких полей не хватает на практике.

## API для чат-ботов (`pb_hooks/api_v1.pb.js`)

| Метод | Назначение |
|---|---|
| `POST /api/v1/programs/validate` | Проверка без сохранения: нормализованная программа с рассчитанным временем + ошибки и предупреждения |
| `POST /api/v1/events` | Создать мероприятие-черновик из документа. Ответ: `preview_url`, **`invite_url`** (ссылка-приглашение), `draft_token` (бот может править, пока черновик не принят), отчёт проверки. Повтор с тем же заголовком `Idempotency-Key` не создаёт дубль |
| `PUT /api/v1/events/{id}/program` | Заменить программу черновика (по `draft_token`) или своего мероприятия (по ключу владельца). Каждая замена сохраняет версию |
| `GET /api/v1/events/{id}/program` | Выгрузить программу в `conf.program/v1`, чтобы бот мог прочитать и доработать |
| `POST /api/v1/events/{id}/invite` | Новая ссылка-приглашение, если старая истекла |
| `POST /api/v1/feedback` | Обратная связь от бота: не хватает функции, ограничение схемы, ошибка, непонятная документация, ложное срабатывание проверки (подробнее ниже) |
| `GET /api/v1/changelog` | Что добавлено в API и схему за последнее время, чтобы бот знал о новых возможностях |

- **API-ключи** (`api_keys`): выдаёте вы в админке. Хранится только хэш.
  - права: `create_events`, `update_own`, `read_own`;
  - лимиты: мероприятий в сутки, размер документа;
  - срок действия, отзыв.
- **Ссылка-приглашение** `#/claim/<token>`, одноразовая, живёт 14 дней. По ней открывается предпросмотр программы и форма «e-mail + пароль» (или вход в существующий аккаунт). Человек становится владельцем мероприятия. Невостребованные черновики удаляются через 30 дней (`cronAdd` в pb_hooks).
- **Мероприятие, созданное ботом, всегда черновик.** Опубликовать его может только человек.

## Обратная связь от чат-ботов

Бот, которому чего-то не хватает, не должен молча изобретать обходной путь. Он сообщает об этом пользователю и сервису.

- **Запрос** `POST /api/v1/feedback` (по API-ключу):
  - `kind`: `missing_feature` / `schema_limitation` / `bug` / `unclear_docs` / `validation_false_positive`;
  - `area`: schema, validate, events, invite, documents, jury или другое;
  - `summary` — одна строка;
  - `details`: что просил пользователь, что бот пытался сделать, что получил;
  - `workaround`: как бот обошёлся, например положил данные в `extra`;
  - `impact`: blocker / degraded / nice_to_have;
  - контекст: версия схемы, endpoint, коды ошибок, путь в документе, `event_id`, клиент и модель («Claude Opus 5.5», «GigaChat»).
- **Без ПДн.** Сервер вырезает e-mail и телефоны и ограничивает размер. Лимит частоты считается по ключу.
- **Ответ боту:** `{id, status, known_workaround?}`. Если вы уже описали обход для похожей темы (тот же `kind` + `area` + сходный `summary`), бот сразу получает его и может предложить пользователю.
- **Источники:**
  - MCP-инструмент `send_feedback`;
  - операция в `openapi.json` для GPT;
  - для ботов без инструментов — массив `feedback` в JSON-ответе, который страница «Создать из JSON» отправляет вместе с программой;
  - автоматически — каждое использование `extra` и каждое предупреждение, которое владелец пометил «ложное срабатывание»;
  - кнопка «Сообщить о проблеме» в интерфейсе для людей.
- **Входящие у вас (`#/admin/feedback`):**
  - группировка похожих сообщений со счётчиком («не хватает: стендовая сессия — 7 раз»);
  - статусы: новое / в планах / сделано / отклонено;
  - поле «обход для ботов».

  При статусе «сделано» запись попадает в `changelog`.
- **Уведомления:** письмо-сводка раз в день. По желанию — сообщение в Telegram о каждом `blocker`.
- **Правило в `/llms.txt` и описаниях MCP-инструментов:** «если функции не хватает — положи данные в `extra`, честно скажи пользователю, чего не хватило, и вызови `send_feedback`; не выдумывай поля и обходы молча».

## Локальная модель: MCP `local-llm` и LM Studio на RTX 5080

У локальной модели в проекте три роли.

**1. Помощник при разработке.** Эти задачи я выполняю через `local-llm`, чтобы не тянуть объёмные материалы в контекст:
- `local_digest`: разбор старых программ и шаблонов из `Nextcloud\__Для статей\РРВ_2023` (программы 2021/2023, протоколы, памятка) и `Downloads` (программа RWP-2026). Из них получаются фикстуры `conf.program/v1` и проверяется, что схема покрывает реальные программы прошлых лет;
- `local_submit`: массовая генерация тестовых данных в фоне — списки заявок в разных форматах, информационные письма в разном стиле, «грязные» Excel-файлы для импорта;
- `local_review`: первичный просмотр диффов. По опыту большая часть находок ложная, поэтому каждую я проверяю сам;
- **правила проверки:** цитаты строк перепроверяются, вычисленные числа и утверждения «чего-то нет» — обязательно. Каждая фикстура проходит `validate` и сверяется с исходником.

**2. Бесплатный «бот» для тестов и замеров качества.** Без расходов на API и без отправки данных наружу:
- `tests/bots/local_bench.mjs`: набор материалов из `fixtures/materials/` (RWP-2026, РРВ-2023, синтетические) → «Набор для чат-бота» → локальная модель → JSON → `POST /api/v1/programs/validate`. Скрипт обращается напрямую к OpenAI-совместимому API LM Studio (`localhost:1234`), той же модели, что стоит за `local-llm`. Разовые прогоны во время разработки я делаю через `local_submit`;
- метрики: доля валидных документов, число ошибок по типам, совпадение с эталоном (доклады, секции, время), заполненность `extra`;
- это замер того, насколько схема и `llms.txt` понятны модели, — до проверки на Claude и ChatGPT. Ухудшение после правки схемы или промпта видно сразу;
- **агентный режим:** LM Studio подключает наш MCP-сервер по stdio (`mcp.json`), и локальная модель проходит весь путь `validate` → `create_event` → `send_feedback`. Это ручная проверка этапа 2.

**3. Локальный обработчик для боевых задач (по желанию, этап 9).** Тяжёлую обработку с ПДн выполняет ваша видеокарта, а не зарубежный сервис:
- задачи: разобрать 50 заявок из docx, нормализовать организации, найти дубли;
- в сервисе есть коллекция `jobs`. Скрипт `worker/` на вашем ПК **сам опрашивает** сервер по API-ключу с правом `process_jobs`. Соединение исходящее, поэтому работает за NAT без проброса портов;
- обработка идёт через локальную модель (OpenAI-совместимый API LM Studio на `localhost:1234`), результат возвращается как новая версия программы или черновик заявок на утверждение;
- если ПК выключен, задача ждёт в очереди. Владелец видит статус и может обработать её вручную.

## Как боты узнают про API

- **`/llms.txt`** — короткая инструкция для бота:
  - что делает сервис;
  - порядок работы: `validate` → исправить → `create` → отдать человеку `invite_url`;
  - правила: не выдумывать докладчиков и время, спрашивать недостающее у пользователя, не передавать контакты без необходимости;
  - ссылки на схему и пример.
- **`/schema/program.v1.json`** — JSON Schema с описаниями полей на русском и примерами. **`/openapi.json`** — для GPT Actions.
- **MCP-сервер `mcp/`.** Инструменты:
  - `get_program_schema`, `validate_program`, `create_event`;
  - `update_event_draft`, `get_event_program`, `new_invite_link`;
  - `send_feedback`, `get_changelog`.

  Промпт-сценарий «Создай программу мероприятия из материалов». Транспорты:
  - **stdio** — Claude Desktop/Code, LM Studio с локальной моделью на RTX 5080; ключ в переменной окружения;
  - **Streamable HTTP** `https://conf.konkin-nikita.ru/mcp` — ключ в заголовке `Authorization`. Для клиентов без настраиваемых заголовков (коннекторы claude.ai) — персональный URL `/mcp/k/<ключ>`: отзывается как ключ, права ограничены.
- **ChatGPT** — Custom GPT с Actions по `/openapi.json` и авторизацией по API-ключу.
- **GigaChat, YandexGPT и любые боты без инструментов.** В конструкторе есть «Набор для чат-бота»: промпт + схема + пример одним текстом. Ответ бота вставляется на странице `#/new/from-json`: JSON извлекается даже из окружающего текста, проверяется и создаёт черновик в аккаунте вошедшего пользователя.

## Модель данных (коллекции PocketBase)

| Коллекция | Главное | Доступ |
|---|---|---|
| `users` (auth) | email, пароль, имя, `is_admin` (вы) | создаются только через ссылку-приглашение или вами |
| `api_keys` | выдавший, название, хэш, права, лимиты, срок, отозван | только админ |
| `events` | slug, `owners` (→users), `status` (draft/published), поля `event`, настройки, `created_by_key`, хэши приглашения и `draft_token`, срок приглашения | published — все; draft — владельцы и админ |
| `event_private` | jury_code, admin_code | владельцы и хуки |
| `program_versions` | event, документ `conf.program/v1`, источник (ui/api/mcp/import), автор, время | владельцы; откат и сравнение версий |
| `rooms`, `sections`, `sessions` | как в документе программы | как events |
| `items` | session, section, **`code`** («s2-3»), type, start, duration, название, докладчик, авторы, format, зал, `competitive`, `status` (planned/done/absent) | как events |
| `people`, `organizations` | справочники; контакты видят только владельцы | — |
| `applications` | заявка, `code`, согласие на ПДн, status | создавать — все (лимит + honeypot), читать — владельцы |
| `scores`, `scores_deleted` | как в jury-score | только через `/api/jury/*` |
| `feedback` | kind, area, summary, details, workaround, impact, контекст, клиент/модель, источник (mcp/api/paste/auto/ui), ключ, `group` (группа похожих), status, ответ | создают боты по ключу и люди; читает и правит админ |
| `feedback_groups` | тема, счётчик, статус, «обход для ботов», запись changelog | админ |

Справочные коллекции — это рабочее представление для конструктора и публичных страниц. Документ программы собирается из них и разбирается обратно функциями `toDocument` / `fromDocument` в `shared/model.js`. Импорт, экспорт и API используют одну и ту же пару функций.

## Модули

1. **Конструктор (`#/admin`):**
   - мероприятия владельца;
   - редактор: дни → заседания → элементы, перетаскивание, авто-время с якорями, автодополнение людей и организаций;
   - панель проверок;
   - история версий с откатом;
   - импорт Excel/CSV с предпросмотром;
   - «Скопировать прошлое мероприятие как шаблон».
2. **Публичная программа (`#/e/<slug>`):** мобильная, в стиле liquid glass. «Сейчас идёт / далее», фильтры, поиск, `.ics`, обновления в реальном времени.
3. **Документы (HTML + print-CSS, A4):**
   - программа как официальный PDF;
   - «на дверь»;
   - протокол секции: №, ФИО, доклад, место работы, форма, примечание; подписи;
   - итоги конкурса;
   - дипломы;
   - выгрузка в Word.
4. **Жюри (`#/e/<slug>/jury`):** перенос текущего модуля. Критерии из `event.jury`, оцениваются элементы с `competitive`.
5. **Заявки (`#/e/<slug>/apply`):** форма, согласие на ПДн, антиспам, модерация. Принятая заявка становится элементом программы.
6. **API и интеграция с чат-ботами** — разделы выше.

## Что переиспользуем из jury-score

- **Стиль** (`index.html`, `<style>`): токены, тёмная тема, `.glass`/`.card`/`.seg`/`.tabbar`/`.toast` → `web/src/css/glass.css`. При переносе `inset` и flex-`gap` заменяются, добавляется режим `lite`.
- **Утилиты** (`index.html`): `LS`, `esc`, `norm`, `clean`, `fmtNum`, `plural`, `hhmm`, `toast` → `web/js/util.js`.
- **Офлайн-очередь жюри** (`change`, `flush`, `beaconAll`, `syncMine`, `normRec`) → `web/js/jury/queue.js`.
- **Итоги** (`computeResults`, `rankRows`, `jurorStats`, `statsHTML`, `downloadCSV`, `deleteJuror`) → `web/js/jury/results.js`.
- **Логика сервера** (`Code.gs`: `save_` с upsert по `ts`, `delete_` с архивом, `roleOf_`, `norm_`) → `pb/pb_hooks/jury.pb.js`, формат ответов `{ok, role, rows, error}` сохраняется.
- **Программа RWP-2026** (`TALKS`, `SECTIONS` + PDF) → `fixtures/rwp-2026.program.json`, эталон для тестов и пример в `/llms.txt`.
- **Тест** `tests/smoke.py` → основа e2e-теста жюри.

## Проверка

- **Юнит-тесты** (`node --test tests/unit`):
  - `fromDocument(toDocument(x)) == x` на фикстуре RWP-2026;
  - расчёт времени и якоря;
  - проверки: на `rwp-2026.broken.json` (`14:45–14:00`) должна быть ошибка с правильным путём, на исправленной программе — ноль ошибок;
  - нормализация «А.О. Рябов» = «А. О. Рябов».
- **API-тесты** (`tests/api`, локальный `pocketbase serve` с временным `pb_data`):
  - без ключа → 401, ключ без `create_events` → 403;
  - лимиты срабатывают;
  - `validate` ничего не сохраняет;
  - `create` с тем же `Idempotency-Key` не создаёт дубль;
  - `draft_token` перестаёт работать после принятия приглашения;
  - приглашение одноразовое и истекает;
  - cron удаляет невостребованные черновики;
  - каждая замена программы создаёт версию.
- **Обратная связь** (`tests/api`):
  - `send_feedback` без ключа → 401;
  - e-mail и телефон в `details` вырезаются;
  - два похожих сообщения попадают в одну группу и увеличивают счётчик;
  - при описанном обходе ответ содержит `known_workaround`;
  - документ с `extra` создаёт автоматическую запись `schema_limitation`;
  - массив `feedback` из вставленного ответа бота сохраняется;
  - статус «сделано» появляется в `/api/v1/changelog`.
- **MCP** (`tests/mcp`): клиент SDK проходит `get_program_schema` → `validate_program` (с ошибкой) → `create_event` → `update_event_draft`, затем открывает `invite_url` (Playwright), задаёт пароль и видит программу. Ручной прогон в MCP Inspector, Claude Desktop и LM Studio.
- **Замер на локальной модели:**
  - `node tests/bots/local_bench.mjs` (LM Studio на `localhost:1234`) выдаёт таблицу метрик по каждому набору материалов;
  - порог: не меньше 80 % валидных документов с первой или второй попытки (после отчёта `validate`);
  - результаты сохраняются в `tests/bots/results/<дата>.json`, чтобы сравнивать с прошлыми прогонами.
- **Сквозной сценарий с настоящим ботом:**
  - Claude получает текст программы RWP-2026 (из PDF) и задачу «создай программу». Результат сравнивается с фикстурой: 23 доклада, секции, залы, перерывы, а сбитое время секции 4 бот должен заметить по отчёту проверки;
  - Claude получает задачу с тем, чего нет в схеме (например, «стендовая сессия с номерами стендов»). Он должен положить данные в `extra`, сказать об этом пользователю и отправить `send_feedback`;
  - для GigaChat то же через «Набор для чат-бота» и вставку ответа.
- **Совместимость со старыми браузерами:**
  - статически при каждой сборке: esbuild с целями браузеров не пропускает неподдерживаемый синтаксис; eslint-plugin-compat и stylelint-no-unsupported-browser-features ловят API и CSS по `.browserslistrc`; проверка размера бандла (≤ 80 КБ gzip для публичной программы и жюри);
  - смоук-тест собранного `dist/` в старом Chromium 61 и 70 (Puppeteer старых версий скачивает такие сборки): страница открывается без ошибок в консоли, программа отображается, жюри сохраняет оценку;
  - экран «браузер устарел» проверяется на эмуляции без поддержки модулей;
  - **ручная матрица на реальных устройствах** (от вас нужен список того, что есть под рукой): iPhone или iPad на iOS 12, Android 5–7 со стандартным браузером и Chrome, Яндекс.Браузер, слабый Android 2 ГБ (режим `lite`).
- **Мобильная вёрстка:** Playwright прогоняет все экраны при 320×568, 360×640 и 390×844. Горизонтальной прокрутки нет, элементы не меньше 44 px, всё работает касаниями (`has_touch`). Десктоп (этап 8) — отдельно при 1280×800.
- **Производительность:** Lighthouse в мобильном профиле (медленный 4G, замедление CPU в 4 раза) для публичной программы и жюри: время до интерактивности меньше 5 с.

  - конструктор на телефоне: правка через нижний лист, перемещение кнопками, откат версии, импорт xlsx;
  - публичная страница при ширине 320 и 390 px;
